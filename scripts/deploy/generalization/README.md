# Competitor generalization release

This QA revision uses a separate `-qa` stage, image/rollback tags, candidate and
workers. Keep the previous stage, worker outputs and rejected cases intact.
The previous read-only candidate must be stopped separately before reusing
localhost port 18081; these scripts never stop or delete an earlier container.

These scripts target `/opt/apps/smartcomp` only. They do not change city files,
container, ports, or Nginx. Runtime credentials remain in the existing production
`.env`; scripts neither copy nor print its contents. Running scripts performs
mutations; reviewing or uploading them does not deploy anything.

Upload the six scripts and `generalization-manifest.json` to
`/home/ubuntu/maintenance/smartcomp-generalization-20261101-qa/` after pushing the
final commit to GitHub. The manifest contract is:

```json
{
  "repository": "Yejiajun277/SmartComp_Engine",
  "baseline": "3621d6f6e2a77c0584dd20407560ea0a6a503320",
  "previous_commit": "a6b6e6ef42d0a06c88954863d07c3b79b42efc95",
  "commit": "<pushed final 40-character lowercase GitHub SHA>",
  "runtime": ["<files to synchronize into the production source directory>"],
  "files": [{"path": "<repository-relative file>", "sha256": "<file SHA256>"}]
}
```

`runtime` is the `a6b6e6ef..commit` source delta, including necessary new tests,
documentation and these release scripts. `files` contains that delta plus all
backend tests required in the candidate image. Every file hash must come from
the exact commit. No `.env`, output, old temporary files or dependencies belong
in either list. The user change summary compares against `3621d6f`; this does
not change the incremental image/source baseline of the current production.

1. Run `sh generalization_stage.sh`. It downloads the exact commit archive from
   GitHub, extracts only manifest-approved files, checks hashes and builds an
   incremental image from `sha256:f4a2a055868d3fe1810a4cd3ee90cf0f77fa7d8f751623540c21b81a845c106a`.
   Its candidate, `smartcomp-generalization-qa-e2e`, binds `127.0.0.1:18081` and
   mounts production output **read-only**. It refuses to replace existing staging
   directories or candidate containers. If GitHub download is unavailable,
   upload `source.git-archive.tar.gz` generated by
   `git archive --format=tar.gz --output=source.git-archive.tar.gz <commit>`.
   The fallback must retain Git's exact commit in its tar PAX comment; the
   stage record names the fallback source and archive hash explicitly.
2. Run `sh generalization_accept.sh`. It runs the full backend suite in a
   disposable container using the exact candidate image, no network, no runtime
   credentials, and a separate temporary output filesystem. It retains the full
   log and a release-bound test record. It compares three historical report JSON
   payloads and collection facts with production, checks rendered citations and
   internal anchors, and verifies source hashes/history/city state. Only success
   creates `generalization-acceptance.json`, binding `pass`, `commit`, exact image
   ID and manifest hash to `stage-state.json`. A previously successful test log
   is reusable only when all release identifiers and its checksum still match.
3. Run `sh generalization_promote.sh`. It requires no active production tasks,
   verifies acceptance/image/commit/files, backs up changed source files, keeps
   all old output hashes, and recreates only `smartcomp-app`. Verification
   failure restores the previous image/source without restoring or deleting
   output. `sh generalization_rollback.sh` performs a later explicit rollback;
   it refuses to overwrite subsequent source edits.
4. Run `sh generalization_worker_start.sh` **after promotion passes**. It starts
   `generalization-vacuum-qa` on `18082` and `generalization-hotel-qa` on `18083`, each
   with its own fresh output directory and the exact deployed image/SHA. It
   does not submit tasks. Submit the two independent category requests in
   parallel using `POST /api/tasks`, `max_competitors: 3`, `skip_qa: false`,
   and `use_rule_engine: false`. Do not expose these localhost ports publicly.
5. Inspect both full real MiMo/Tavily runs, their artifacts, report JSON/HTML and
   QA. For each phase, the final attempt must have `passed: true`,
   `degraded: false`, `hallucination_status` equal to `passed` or `found`, and no
   critical issues. `found` may retain warnings. Failed, skipped or missing
   hallucination checks cannot pass live acceptance. Earlier failed attempts and
   critical findings remain in the immutable audit; a genuinely corrected final
   attempt can pass. These new-case rules do not retroactively judge the old
   historical reports used only for the staging consistency comparison.
   Write `generalization-live-acceptance.json`:

   ```json
   {
     "pass": true,
     "commit": "<exact deployed SHA>",
     "candidate_image": "sha256:<exact deployed image>",
     "manifest_sha256": "<exact candidate manifest hash>",
     "tasks": [
       {"worker": "generalization-vacuum-qa", "task_id": "<completed ID>", "pass": true},
       {"worker": "generalization-hotel-qa", "task_id": "<completed ID>", "pass": true}
     ]
   }
   ```

6. Run `sh generalization_import.sh`. It independently requires completed,
   real-mode, QA-on count-three tasks and the exact final-attempt rule above for
   every phase, including hallucination completion and absence of critical issues.
   All task/run destinations must be new. It copies complete runs before task
   records, verifies copied bytes and all previous output hashes, then recreates
   production with the **same image** to reload history. It never imports failed
   cases or overwrites an existing task. A failed import leaves an explicit
   `import-state.json` and retained artifacts for review; it does not delete
   existing history or silently retry an earlier partial import.

Keep `stage-state.json`, `promotion-state.json`, `workers-state.json`, the two
acceptance records, `import-state.json`, source backups and build logs as the
release record. These files contain provenance and hashes, not credentials.
